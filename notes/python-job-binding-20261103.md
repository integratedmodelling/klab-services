## Reproduced client defect and fix

At the unchanged base, a Job re-read its mutable Context scope, service, numeric
ID, executing endpoint and configured home Runtime from live Python objects for
every request. Mutating the Context scope could silently redirect an existing
Job to the same number in a different scope. Added the regression test first;
the sync and async scope-token status cases both failed (DID NOT RAISE) because
the old implementation sent HTTP rather than reject the changed scope.

The committed `_job_binding.py` captures a private immutable construction-time
binding. Guard checks cover status, result, cancel, `Job.to_handle` and direct
`to_handle(job)` calls; read responses and custom result decoders are also
checked before their outputs can escape. A cancellation response received after
binding drift remains SubmissionOutcomeUnknown, with no automatic resend,
rollback or locally accepted cancellation flag. Existing compatible offline
same-Runtime cross-client capture and original handle-identity checks remain.

This is an anti-rebinding comparison, not a durable intent ledger, authenticated
principal, server incarnation or retained-Job generation guarantee. Restoring
exact original local configuration can permit operations; no continuous drift
observer/latch exists. New objects/private-state replacement are not prevented.

scope/base/credential references cannot poll/retrieve/cancel another identity;
only the separately bound second Job may cancel its own fixture state. This is
**synthetic HTTP**, not two Java deployments or actual retained work.

`python-job-binding-evidence-20261103`; reproducibility depends on committed
